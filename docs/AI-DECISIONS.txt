# Architectural Decisions

- Target framework remains .NET Framework 4.7.2 to match RimWorld's modding
  sandbox.
- Solution intentionally links metadata XML and documentation assets for
  visibility in Visual Studio.
- Added an xUnit-based regression project that validates XML defs without
  needing RimWorld binaries so Codex can run automated checks in CI-friendly
  environments.

2026-10-12 Claude: Batshittium Ballista (v0.7), spec agreed with Matt
"Breakpoint" Heck: power is linear in units = count x range / 10, from
50 W standby / 1,000 W per volley at the baseline to 62.5 kW / 990 kW at
256 bolts and 325 tiles (a quarter of one reactor at standby; four reactors
less 10 kW of magazine feeding at full fire). Implementation choices:
- Subclass Building_TurretGun; give each Ballista its own clone of the
  gun's VerbProperties so range is per building (vanilla shares one per
  Def). Range presets skip 80-89 because vanilla draws cell rings below 90
  tiles and the engine caps them at ~79.8; at 90+ a circle outline is drawn.
- The firing draw is a one-second PowerOutput spike per volley. Before a
  volley the grid must cover it from surplus or stored battery energy, or
  the Ballista holds fire with a message.
- Bolt stores (16 internal, 2,560 per magazine) are bookcase-style haul
  destinations. ThingOwner accepts any amount, so CappedThingOwner caps
  GetCountCanAccept and TryAdd; haul jobs size themselves from it.
- Magazines connect by shared edges, chained (Core.MagazineNetwork); a
  volley drains magazines nearest-first, then the internal reserve.
- The Artificer is a comp on a plain building fed by CompRefuelable;
  outputs are gated per bolt research.

2026-10-13 Claude: Self-destruct aftermath, after Matt "Breakpoint" Heck
found the blast "just sort of a shockwave". Root cause: in 1.6 a Bomb
explosion destroys every Fire it touches (DamageWorker.ExplosionDamageThing),
and the old code lit the fire blanket at detonation, so the expanding wave
put it out. MapComponent_SelfDestructAftermath now lights the same fires
(same chance and size) three ticks behind the wave front, using vanilla's
timing (1.5 ticks per tile at speed 1), and sets off secondary explosions
at 15 per second inside the expanding circle and for 4 s after. The
secondaries are XML entries (Flame bursts, BombSuper at 40 and 80 damage);
BombSuper looks like Bomb but is not caught by the fire check. Timing and
sampling live in Core.BlastSchedule with unit tests. The aftermath is saved
with the map.

2026-10-13 Claude: Singularity fixes from Matt "Breakpoint" Heck's play
test (overnight session).
- The "cycling horizontal line of items" beside the singularity: in 1.6,
  GenSpawn.Spawn of an item into a full cell shoves the cell's item aside
  (GenPlace Near, always searching in the same order, hence a line) or
  destroys it if there's no room. Pulling items into occupied cells churned
  them every step and destroyed stock (the smoke test, run against the old
  code, saw 475 moves away from the centre and all 40 steel lost). Items
  now move only into a cell with room, or merge into a matching stack
  there, and otherwise wait; ripped-loose packages are placed, not
  spawned.
- The log errors: minified buildings tick inside their packages in 1.6
  (MinifiedThing is TickerType.Normal and ticks its contents), and the
  reactor's heat code ran with no map: a NullReferenceException every 250
  ticks. That also hit any reactor uninstalled in normal play. The
  reactor, Artificer, Ballista and Magazine ticks now return when not
  spawned (the replicator and self-destruct already did).
- The smoke script missed it because it attributed errors by their first
  line only ("Exception ticking MinifiedThing123"); it now also reads the
  stack trace. New runner checks: every device ticks packed without an
  error (via Log.Messages), and a pull shoves nothing away and loses
  nothing. All three were confirmed to fail on the old code first.
- Pawns are now seized from the singularity's first tick (caught and held
  stunned), so nobody strolls out while the drag is still slow.
- The vortex gained a fainter, larger outer layer spun the other way, and
  both layers throb four times, harder each time, in the final second
  (Core.SingularityPull.FinalPulse, unit tested).

2026-10-14 Claude: Showcase API, slice 3000 (the game side). Decisions:
- One showcase window is open at a time: moving between the three levels
  replaces the window, so Back returns one level and Escape (which closes
  the open window) closes the whole menu, as specified.
- Force start (a confirmed second button beside Start, for a fatal flag
  only) is offered in dev mode or when the game was started with

  showcase flagged fatal. Missing requirements cannot be forced.
- The caption bar is drawn at the top centre, just below the colonist
  bar, not at the bottom as SHOWCASE.md proposed: the bottom holds the
  gizmos of the subject the director selects, the inspect pane and the
  main buttons, and a bar there would cover them and take their clicks
  (GameComponentOnGUI runs before the window stack).
- Autosave is suppressed without Harmony: the session resets the
  autosaver's private ticksSinceSave counter by reflection every tick,
  before Autosaver.AutosaverTick runs in TickManager.DoSingleTick, so it
  never reaches the shortest interval (0.05 days). If RimWorld renames the
  field, the session warns once. Nothing about the session is saved, so
  a showcase game the player chooses to save loads as an ordinary game.
- The launcher repeats vanilla's dev Quick Test (a "GeneratingMap" long
  event running Root_Play.SetupForQuickTestPlay, then
  PageUtility.InitGameStart), setting the def's map size and, when it
  names a biome, a random valid tile of that biome (else the random tile,
  logged). The request is tied to the Game object it generated, so a
  failed generation can never turn the player's next real colony into a
  showcase.
- Log cues keep the [BT-SHOWCASE] prefix while the API lives in this mod,
  so capture tooling has one vocabulary: LAUNCH, GAME, START, READY,
  SCENE, END, SKIPPED, SKIP, FINISHED, STOPPED, FAILED, REFUSED, BIOME.
  READY is now the API's, logged once the worker is set up.
- Keyed strings are prefixed BT_Showcases_ and live in
  Languages/English/Keyed/BT_Showcases.xml; a framework mod split out

2026-10-13 Claude: Tractor Bomb step 2, the reusable implosion. The
singularity grenade's pull now lives in Implosion (Source/Implosion.cs),
an IExposable that a host thing owns, ticks once per tick and saves with
Scribe_Deep; SingularityField is its first host. Decisions:
- Its settings are a plain class in Core, ImplosionSettings (pullRadius,
  gatherRadius, pullTicks, pullRateStart, pullRateEnd, ripFixtures,
  ripTicks), so a Def can carry them in XML and Dial-A-Yield can adjust
  a copy. The defaults are the grenade's. Every implosion works from
  Normalized() settings (radii within the engine's limit, the gather
  radius within the pull, rates from 0 to 60 cells per second and never
  slowing), and a Def reports Problems() as configuration errors. Both
  are unit tested, including that normalized settings are always sound.
- The implosion never ends itself; its host decides. The grenade ends at
  TimeUp. A host may end early on AllGathered (everything in reach within
  the gather radius, as of a drag step taken after the rip reach was
  complete) or Settled (a drag step moved nothing: everything is gathered
  or stuck, the Colony Bomb's "a full pass moves nothing"), or stop at a
  cap of its own. Past TimeUp the drag keeps its end rate.
- The gather radius is a target, not a stopping line: gathered things
  keep settling toward the centre, so a large gather radius never leaves
  a hollow ring. A thing blocked just outside it may slip sideways into
  any free cell inside it (Core.ImplosionMath.StepsInward). Without the
  slip, items converging along one axis queued outside a 1.5-tile pile:
  a control build without it failed the new smoke checks with a
  component and a silver stack stuck at (0, 2) and (0, 3). With a gather
  radius of 0 the steps are exactly SingularityPull.StepsToward's (unit
  tested from every offset), so the grenade moves things as before.
- The grenade's numbers, visuals and smoke checks are unchanged. Its
  diagnostics (StepsTaken, Uninstalled, TornDown, ItemsMoved,
  CaughtCount) read through to its implosion; SurvivorsComforted stays a
  static on the field. One deliberate difference: a plant that cannot be
  destroyed is now left alone, as other indestructible things already
  were.
- A field saved mid-pull before this change has no implosion; on load it
  opens a fresh one and pulls for its full five seconds.
- A new smoke check hosts an implosion directly in the runner, with the
  Tractor Bomb's 10 tiles in to 1.5, so the groundwork is tested before
  the bomb exists.

  hit, so it keeps no hit points (useHitPoints stays false) and damage

2026-10-14 Claude: Tractor Bomb multi-bomb physics (ROADMAP.md, step 11,
"Multi-bomb physics"; docs/TRACTOR-BOMB.md, "As Built"). Decisions:
- Durations live in ImplosionSettings (minDurationTicks,
  maxDurationTicks), not in each host, so every implosion has them and a
  Def can set them; Core's ImplosionMath.IsOver decides and
  Implosion.Over reports. The Tractor Bomb runs 2 to 8 s (the roadmap's
  proposal), replacing TractorBombTiming's 7.5 s cap, which is gone. The
  grenade's minimum and maximum are both its ramp, so it ends exactly when
  TimeUp said; saves from before the durations get that rule too.
- Superposition is a potential: each pull contributes its rate times the
  distance to its centre, and the net pull the roadmap describes (a unit
  direction per centre scaled by its rate) is that potential's downhill
  slope. A step must go strictly downhill, which for one pull is exactly
  "strictly closer to the centre" (checked in whole numbers), so the
  lone-pull guarantee does not depend on the jitter at all, and no cycle
  can repeat while the weights hold. Allowed steps are tried in order of
  how well they line up with the jittered net direction, so the best is
  that direction rounded to a grid step.
- With constant-strength pulls, two equal ones cancel along the whole
  line between their centres. That is the physics the roadmap asked for,
  so things in the overlap gather on that line and creep along it at the
  few per cent the bias gives them; the 8 s maximum ends the tug-of-war.
- The drag moved to a map-level owner, MapComponent_Implosions
  (Source/ImplosionField.cs). Implosions still seize, rip and keep their
  own clocks and save themselves; the first to tick in a game tick drags
  everything once. Each thing keeps its own step clock at its net rate
  (saved by thing id), and a newly caught thing joins the strongest
  pull's clock, so under one implosion everything steps exactly when the
  old shared clock said: the grenade's and the single bomb's smoke checks
  pass unchanged. Implosions not ticked for a tick drop out; hosts close
  theirs when they explode or leave, so a survivor's pull lurches free at
  once.
- Settled now means every thing in reach either sits on the centre or
  failed its last try to step (restless otherwise), counted on the
  implosion's own clock. Under one pull that is what "the last step moved
  nothing" meant; under two, a thing creeping at a balance point keeps
  both unsettled, as the roadmap expects.
- The jitter's strength part is a per-thing preference order among the
  pulls it feels, 4 per cent apart (hashed from the thing's id and each
  implosion's seed), not an independent random per pull: independent
  biases can come arbitrarily close, and then the flicker, not the bias,
  would decide, so a thing at a midpoint could hover. With the order and a
  flicker of 1 per cent, the bias always decides, as the roadmap's "at a
  balance point, the bias decides which pull wins" and "always tips off
  within a few steps" ask. Turns: 6 degrees persistent, 3 flicker, 9 in
  all, under the 22.5 that would let rounding pick a slower step. The
  flicker is RimWorld's Rand in game and a seedable SplitMix64
  (SeededUnitRandom) in the tests, through Core's IUnitRandom.
- Stretching (optional in the roadmap) fitted cleanly, so it is built: a
  pawn under more than one pull is checked once a second, and the damage
  follows Core's Tension (the pulls' rates less their net pull, a pull it
  sits at the centre of holding it up to its own rate): none to 6 cells a
  second, a point per 6 beyond, at most 4. BT_Stretch has no armour
  category, so armour does not help; it leaves BT_StretchMark. The
  instigator is the strongest pull's (the bomb).
- Found by the twin-bomb smoke test, and fixed in the shared implosion:
  ripping a shelf holding several stacks made RimWorld's Building.DeSpawn
  re-place the extra stacks near, often away from the pull (and drop any
  it found no room for). A fixture whose cells hold more stacks than bare
  ground can now waits to be ripped until the drag has taken them off.
- The twin-bomb smoke scenario: armed raiders (Mercenary_Gunner, given a
  rifle if they have none) under a defend-point lord that never flees,
  stunned until both robots have planted so the robots arrive whole (the
  test is of the physics, not the robots' survival), then free to react
  as rolled for two and a half seconds. The countdowns are held at 30 s
  while the robots come and both pulls are started on the same tick
  (ImplodeNow), so the two are equally strong and the overlap is a true
  tug-of-war. RimWorld's Rand is pushed to a fixed seed for the scenario
  and both bombs' hostile rolls use it. Moves are judged only on ticks
  when the same pulls ran before and after; a move under several pulls
  may raise their unjittered potential by no more than the jitter allows
  (with each pull's rate from before or after the tick, whichever is
  kinder, since the drag runs mid-tick). The overlap's end is judged when
  the first bomb goes off: each thing that was ever under both pulls must
  be merged, tipped off to one bomb, in a pile (within 4 tiles of a
  centre), at a balance point (net pull at most a tenth of the pulls'
  sum), or blocked (every clearly downhill cell full), now or within the
  last 15 ticks; and at least one must be at a balance point, which a
  drag that ignored all but one pull fails. Loss is a fall in the junk's
  totals on a tick with no explosion spreading before or after it (an
  explosion destroys itself on the tick it affects its last cells).
- Proof: every new unit test and smoke check was run against a sabotage
  first (Core: lone steps that may go away, no bias, truncated rounding,
  unseeded noise, flicker as large as the bias, steps not downhill, only
  the first pull counting, 30-degree turns, the minimum ignored; smoke:
  no maximum, a late maximum, items spawned into full cells, items lost,
  steps away from the strongest centre, only the first pull counting,
  short stuns, a 1.5 s pull, pulls not closed, an error logged, a bomb
  that never goes off, no stretching, stretching under one pull). Each
  failed the check it was aimed at.
