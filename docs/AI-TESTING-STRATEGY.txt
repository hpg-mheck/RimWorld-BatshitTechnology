# Batshit Technology Testing Strategy

How to exercise the mod, from fastest to most thorough. All three layers
run on a Windows machine with RimWorld installed and RIMWORLD_DIR set.

## 1. Unit and XML regression tests (seconds, no game needed)

    dotnet test Tests/BatshitTechnology.Tests/BatshitTechnology.Tests.csproj

- Core library logic: WeightedSelector, ReactorHeat, and whatever else
  moves into BatshitTechnology.Core.
- XML regression tests over Defs/, About and Textures/: the corrected v0.2
  values (so those bugs cannot return), research, recipes, the reactor,
  every BT_ cross-reference, every mod texture path, and two RimWorld
  config rules found by the smoke test (impassable buildable buildings need
  fillPercent 1; minifiable buildings need a thing category).

## 2. Def validation against the game assembly (under a minute)

    powershell.exe -NoProfile -ExecutionPolicy Bypass -File Tools\validate-defs.ps1

A static stand-in for RimWorld's XML loader. Every element must map to a
real field of the 1.6 game types (nested objects and [LoadAlias] included),
enum values must parse, classes must resolve, Def references must exist in
vanilla or the mod, and texture paths must resolve. Exits 1 on problems.
It cannot run RimWorld's own ConfigErrors logic; layer 3 covers that.

## 3. In-game smoke test (about three minutes)

    .\Tools\smoke-test.ps1

Launches RimWorld in a window with an isolated save-data folder (the
player's config, saves and mod list are untouched), links the repository
into Mods, and starts a quick-test map. The -btsmoketest runner
(Source/SmokeTest.cs) then builds each device, drives real game ticks and
logs [BT-SMOKE] PASS/FAIL lines: reactor output and burn cycle, power
connection, Transmogrifier bills, replication, refrigeration and its power
draw, hauling, ejection, room heating, and the self-destruct countdown,
abort, detonation and aftermath (fires surviving the shockwave, secondary
explosions inside the circle; with timing), the reactor's bolt barrage
(every volley inside the radius; timed), damage triggering a self-destruct,
an armed device destroyed by damage going off, a thrown Ergonomic
Singularity Grenade (singularity opens, a wall is torn down and a stool
uninstalled, a steel stack and a colonist are dragged in, it explodes and
the surviving colonist gets the memory), and each device's pulverization
blast (rock spewed, colonist stunned, bolts cooked off and
none spilled, half-made bolts sprayed). It also packs up (minifies) every
device and ticks the packages, watching RimWorld's log queue for errors,
and checks a singularity's pull shoves no item away and loses none. The
script counts an error as the mod's when its line or its stack trace
mentions the mod or carries the Showcase API's [BT-SHOWCASE] prefix;
RimWorld 1.6 puts a "[Ref 9E9A3C82]"-style line between an error and its
trace, which the script reads as part of the trace. As its last check the
runner reads RimWorld's own log queue and fails on any error (or any
warning about the mod or about statically held assets) logged during the
run, since Player.log does not mark errors as errors. Before the
destructive tests the runner removes the other devices with
DestroyMode.Vanish, so a random 5% damage trigger cannot set one off
mid-test. The script reports those lines plus every error in the game log
and exits 1 on any failure or mod error. Use -KeepOpen to look around
afterwards, or -Showcase to skip the tests and start the BT_Showcase
showcase through the Showcase API instead (-showcase=BT_Showcase: the demo
base of Source/Showcase.cs), with sound on. Both are for a person to
watch, so the game window is maximized (once the runner reports DONE or
the showcase logs [BT-SHOWCASE] READY) and the UI is scaled 2x; plain test
runs stay small and muted.

The runner also builds AnyRim, the showcase's test town, after the
non-destructive tests: it checks the build report, every placement,
enclosed and reachable rooms, roofs, the firebreak, power, the reactor's
heat ring, the eight residents and their lords, the census, and a clean
demolition, then takes the town down before the destructive tests, whose
blasts would reach it. The town's geometry is unit tested in Core
(TownPlanTests, TownSiteTests and others), including a catalogue check
against RimWorld's own Defs where the game is installed.

Last of all, the runner checks the Showcase API
(Source/SmokeTestShowcases.cs). Its test showcases are made in code,
added to the def database under this mod beside BT_Showcase, and removed
again afterwards; an XML test pins that none is ever shipped. Ticking
inside the frame, it checks that the menu button is the mod's only
Harmony patch (from Harmony's own patch listing); that in-game launch
verdicts match Core's (a fatal flag refuses, Force start overrides it, a
missing required mod makes a showcase unavailable even when forced, a
concern warns); that a four-scene director showcase, run through the
game's own session, frames a cut shot, selects its subject, captions
"2 of 4", obeys Skip, times out a scene that never ends, logs its cues in
order to FINISHED, and says each outcome's narration before the closing
message; that the session writes nothing into a save; and that a
showcase game never reaches its autosave. Then it runs a few real
frames, for what only drawing and input show: the caption bar paints;
vanilla's main menu, drawn off screen with the program state set to
Entry for that one call, gets exactly one Showcases button, and the
in-game menu none; the button's own action opens the three windows,
which list the mod and its showcases, grey out the missing-mod showcase
with its reason, refuse the fatal one while offering Force start (dev
mode is on), and honour Back and Escape (a real key-down event is made
current while the window stack handles the cancel key); Stop ends a run
with no later scene; a stopped showcase game still never autosaves, an
ordinary one does, and the autosave setting is unchanged; and, 30 frames
later, when a queued autosave would have been written, the save folder
has gained and changed no files. DONE waits for these frame steps, for
120 seconds at most. Every one of these checks was seen to fail against
a sabotaged build (docs/AI-DECISIONS.txt, 2026-10-14, slice 6000).

Notes for extending the runner: it ticks inside a single frame, so
per-frame engine work must be triggered by hand (power-net wiring:
PowerNetManager.UpdatePowerNetsAndConnections_First). Destructive
scenarios go last. Checks that need drawing or input run as frame steps
(FrameStep in Source/SmokeTestShowcases.cs), each in a frame update or
in a repaint event: GUI calls need a repaint event, and Event.Use()
belongs on input events only, never on a repaint or layout event.
